WEB Technologies 1 (Front End) -Assignment 4–5
JavaScript fundamentals · arrays, loops & functions · DOM · events · form validation
Main requirement: treat it as a real project
Continue the same website, team, real organization and Git repository used in Assignments 1–3 and the Midterm Project. The result must be a complete, logical and usable front-end product for that organization—not a collection of JavaScript demonstrations.
•	Review every page and every visitor journey. Add functionality wherever a real visitor needs to search, choose, calculate, submit, confirm, edit or remove something.
•	Consider the complete logic of every feature: initial state, user input, valid result, invalid result, empty state, repeated action and final confirmation.
•	Every action must finish clearly. No dead buttons, blank result areas, unfinished forms, meaningless effects or features unrelated to the organization.
•	All data, prices, services, schedules, restrictions and messages must be realistic and consistent across the whole site.
HTML/CSS freeze
•	Start from the midterm tag. Do not directly add, delete or rewrite interface elements in HTML files; only script links may be added.
•	Do not add or delete CSS rules. Create, insert, update and remove new elements through JavaScript DOM methods.
•	Change visual states through classList using the CSS classes prepared at midterm. Do not generate CSS rules or use element.style to replace missing CSS.
•	Document any essential midterm correction in README before using it; the correction receives no points.

Planning and individual contribution
•	Add a Functionality Plan to README: page, visitor goal, planned function, expected result and responsible student.
•	Each student implements at least two substantial features on their pages. The team implements at least one shared site-wide feature.
•	A substantial feature completes a visitor task. A colour change, alert, console output, decorative animation or isolated random value does not count.
Required JavaScript
•	Create a js folder; use main.js for shared behaviour and clearly named page-specific files. Load scripts with defer and use 'use strict'.
•	Use const by default and let only for changing values. Do not use var, ==, !=, inline event attributes or document.write().
•	Use an array of at least six objects with real project data and at least four meaningful properties per object.
•	Use a loop/traversal and operations that filter, find, transform or total data.
•	Write at least four reusable functions with parameters and return values; at least one function calls another.
•	Use arithmetic, if/else or switch, at least two logical operators, === and !== in meaningful project logic.
•	Use Math.random() meaningfully, for example for a featured item or temporary reference number; it must not create a false business promise.
•	Render repeated cards, rows, items or options from the array through one reusable function and DOM methods.
•	Use textContent for user-provided text. Never insert user input through innerHTML.
Required interactive functionality
•	Add useful search, filter, sort or category controls. Show the result count, no-results state and reset option.
•	Add a meaningful calculation or selection flow: total price, quantity, duration, participants, selected services or another theme-related result.
•	Use addEventListener() and at least three event types: submit, click and one appropriate event such as input, change or keydown.
•	Use DOM methods to create/remove elements and classList for hidden, active, selected, error and success states.
•	Every generated list must have an empty state. Every user action must produce clear feedback. The console must contain no errors.
Form validation
•	Complete one important form flow: input → field-level validation → invalid/valid state → useful confirmation.
•	Validate at least four fields: trimmed required text; email or telephone; numeric, date or selection rule; and one rule comparing/combining fields.
•	Show specific errors beside fields, focus the first invalid field and clear outdated errors. alert() is not accepted as validation output.
•	On success, show a summary of the visitor's choices. State that no data is sent to a server and no real booking, payment or order is created.
Theme-specific requirements
Implement every module that logically applies to the chosen project.
Reviews/comments
•	Create each review as a separate card through one function. Existing and newly submitted reviews use the same rendering function.
•	Show name, text, rating/category where relevant, and automatic date/time. Validate content and length and show a character counter.
Menu/catalogue
•	Render real items from an array. Provide at least two connected controls such as category filtering plus search, sorting or availability filtering.
•	Show matching count, no-results state, reset option and a meaningful next action for the selected item.
Cart/order
•	If the project sells products, food, tickets or services, show the cart in a prepared Bootstrap modal or equivalent prepared container.
•	Allow add, quantity increase/decrease, remove and clear. Recalculate line subtotals, total quantity and final total after every change.
•	Show an empty state, disable checkout when empty, display a summary and produce only a demonstration confirmation/reference number.
Booking/appointment
•	Validate dates, participant counts and related selections; reject past dates and conflicting or impossible values.
•	Show a live summary with selected service/event, date, time, quantity and calculated price where relevant.
•	Present success as a demonstration request, not a confirmed real-world booking.
Login/registration
•	Required only when these pages already exist and are logical. No database is required; implement front-end validation only.
•	Use regular expressions to require at least eight characters with uppercase, lowercase, digit and special character; show a live checklist.
•	Require exact password confirmation and an accessible Show/Hide Password control.
•	Do not claim that an account was created or a user authenticated. Show an explicit front-end demonstration message.
•	Never store passwords in localStorage/sessionStorage or arrays, place them in a URL, print them or include them in output.
Quality requirements
•	All controls work by keyboard and actions use real buttons. Dynamic messages do not rely on colour alone.
•	Generated content works at approximately 375 px, 768 px and desktop width without horizontal overflow.
•	HTML/CSS remain valid; all links, images, forms and Bootstrap components work.
Forbidden
No jQuery yet, other libraries/frameworks, copied widgets, templates, AI-generated code, eval(), document.write(), inline events, unsafe innerHTML with user input, fake authentication, databases or server-side code.
Submission and defense
•	Submit the same repository with js folder, README/Functionality Plan, JavaScript checklist with exact files and line numbers, evidence, AI log and assignment-4/assignment-5 tags. Keep the midterm tag unchanged.
•	Each team member makes at least four meaningful commits across three days; an individual student makes at least six.
•	At defense, every student explains code from any team page, traces input to result and performs a small live change. No defense or inability to explain the code results in zero.
